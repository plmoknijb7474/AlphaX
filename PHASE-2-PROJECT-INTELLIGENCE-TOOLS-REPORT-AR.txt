Alpha — المرحلة الثانية: أدوات Project Intelligence
====================================================

نطاق المرحلة
------------
تم ربط مجموعة أدوات Project Intelligence بمسار الكاتب والمراجع، مع الحفاظ على AI Chat وWorkspace من المرحلة الأولى دون تغيير.

الأدوات المتاحة
---------------
1) Project Files: تحليل المرفقات الفعلية وفهرسة الملفات والاعتماديات ونقاط الدخول.
2) Code Generation: إنشاء ملفات كاملة وفق بنية JSON المتفق عليها.
3) Code Modification: إعادة ملفات كاملة معدّلة مع الحفاظ على الملفات والسلوك غير المطلوب تغييره.
4) Code Testing: خطة اختبار وفحص ساكن لصياغة Python وJSON وHTML؛ لا يشغّل التطبيق أو كود المستخدم.
5) Error Detection: تحديد العيوب المدعومة بمصدر أو نتيجة فحص واضحة.
6) Debugging: تتبع السبب الجذري انطلاقاً من السجلات والشفرة المرفقة، مع فصل الوقائع عن الفرضيات.
7) Apply Patch: معاينة Unified Diff للملفات المقبولة، ثم إنشاء ZIP جديد بعد تأكيد المستخدم. لا يتغير الملف الأصلي أو GitHub.
8) README Generator: اختياري لإنشاء/تحديث README.md عند وجود معلومات موثقة.
9) Requirements Management: اختياري لمراجعة manifest وإرجاع نسخة كاملة منه عند الحاجة؛ لا يتم تثبيت الحزم.
10) Docker Configuration: اختياري لإنشاء Dockerfile و.dockerignore بناءً على المشروع؛ لا يتم تشغيل Docker أو النشر.

التكامل
-------
- تُرسل الخيارات المختارة مع طلب Project Intelligence.
- تُضاف توجيهات الأدوات المختارة إلى System Prompt الخاص بالكاتب، وتضاف قائمة مراجعة مستقلة إلى Prompt المراجع.
- تظل تعليمات System Prompt العامة أعلى أولوية من توجيهات الأدوات، ومحتويات الملفات المرفقة بيانات غير موثوقة وليست تعليمات.
- Project Files يعمل تلقائياً؛ الأدوات الأساسية محددة افتراضياً. README وRequirements وDocker اختيارية.
- Apply Patch عملية منفصلة بعد ظهور الملفات الناتجة: تتطلب ZIP مرفقاً، ومعاينة صالحة، ثم تأكيداً مستقلاً.

قيود المرحلة
------------
- لا يوجد Shell أو Terminal أو Command Execution أو Python Execution أو Package Installation أو Virtual Environment أو Docker runtime في هذه المرحلة؛ هذه أدوات المرحلة الثالثة.
- فحص الكود مبدئياً ساكن، ولا يستورد أو يشغّل ملفات المشروع.
- لا يتم تعديل مستودع GitHub أو ملفات الخادم مباشرةً. Apply Patch يعيد ملف ZIP جديداً للتنزيل.
- ملفات الأسرار والمسارات غير الآمنة والملفات الثنائية تُرفض من Apply Patch.

التحقق
------
- اختبارات Python الوحدوية: تجرى ضمن tests/ باستخدام unittest.
- فحص الصياغة: py_compile لملفات Python.
- فحص الواجهة: Jinja render للواجهة ثم node --check للـJavaScript المضمن.
- لم يتم اختبار HTTP حي أو حسابات/مفاتيح Xkiro أو Supabase/Render في بيئة البناء.

نتيجة هذه الجولة النهائية
-------------------------
- 76 اختبار unittest نجح؛ لا توجد اختبارات فاشلة.
- py_compile نجح لملفات التطبيق والوحدات المرتبطة.
- تم عرض قالب Jinja: 688150 بايت تقريباً، و121 معرّف DOM دون تكرار.
- ظهرت الأدوات العشر في واجهة Project Intelligence، بما فيها Apply Patch.
- فحص JavaScript المضمن عبر node --check نجح.
- أضيف اختبار يمنع أن يؤدي استبدال ملف كبير إلى تجاوز حد الحجم غير المضغوط للأرشيف.
- لم يُشغّل HTTP حي لأن Flask غير مثبت في بيئة الفحص. لم يتم اختبار Xkiro أو Google أو Supabase أو Render الحقيقية، ولم يُرفع شيء إلى GitHub.

# Alpha — Alpha 3.1 Max + Alpha 2.7 Flash

تطبيق دردشة Flask متعدد المستخدمين، مع مفاتيح API منفصلة لكل نموذج ولوحة تحكم مشرف. يدعم التشغيل المحلي على SQLite والنشر على Render مع PostgreSQL في Supabase.

## النماذج الظاهرة للمستخدم

1. **Alpha 3.1 Max** — الإصدار الأساسي مع مسار احتياطي تلقائي عند تعذر الاتصال.
2. **Alpha 2.7 Flash** — الإصدار السريع للمحادثات والمهام اليومية.

## المميزات المحفوظة

- لوحة مشرف ومستخدمون منفصلون، وتخصيص مفاتيح API لكل مستخدم.
- حتى 8 مفاتيح اتصال لكل نموذج بترتيب أولوية، وتحويل تلقائي للمسار الاحتياطي عند فشل الاتصال الحالي.
- System Prompt عام واحد يطبّق على جميع النماذج ومسارات AI Chat وProject Intelligence وDev Code والمراجعة والإصلاح واستدعاءات أدوات الذكاء الاصطناعي، مع إمكانية إضافة تعليمات تخصصية أقل أولوية لكل إصدار.
- الاستدلال في Alpha 3.1 Max تلقائي؛ إعداد التفكير اليدوي يبقى متاحاً لـ Alpha 2.7 Flash.
- مستويات التفكير لـ Alpha 2.7 Flash، وUNLAZY.
- مراجعة الكود وإصلاحه تلقائياً، Diff Viewer، والمرفقات والصور والملفات.
- ذاكرة محادثة مشتركة بين النموذجين لآخر 80 رسالة لكل مستخدم.
- **أدوات AI Chat — المرحلة الأولى:** نماذج أسئلة تفاعلية باختيار إجابة أو كتابة نص، مع أزرار التالي والتخطي والإرسال.
- **استوديو البرمجة الاختياري:** خمسة أوضاع مساعدة (خريطة المشروع، تحليل التأثير، خطة الاختبار، مراجعة التغييرات، وطبيب السجلات)، وكلها متوقفة افتراضياً ويختار المستخدم ما يفعّله.
- **Workspace لكل محادثة:** إنشاء ملفات نصية وتعديلها وحفظها وتنزيلها وحذفها، مع زر لحفظ كتل الكود الناتجة من ردود Alpha. الملفات معزولة حسب المستخدم والمحادثة، ولا تُنفّذ تلقائياً.
- حدود Workspace: 200 ملف لكل محادثة، و2 ميغابايت للملف، و20 ميغابايت إجمالاً. تُرفض مسارات اجتياز المجلدات وملفات الأسرار والمفاتيح والبيانات الثنائية.

## التشغيل المحلي

```bash
python -m pip install -r requirements.txt
export ADMIN_USERNAME=admin
export ADMIN_PASSWORD='ضع-كلمة-مرور-قوية-هنا'
python app.py
```

افتح `http://127.0.0.1:5000/login`.

## النشر على Render + Supabase

راجع الدليل التفصيلي: `DEPLOY-RENDER-SUPABASE-AR.md`.

تنبيه: Render Free قد يوقف الخدمة بعد 15 دقيقة من عدم النشاط، وSupabase Free قد يوقف قاعدة المشروع عند انخفاض نشاطها على مدى أسبوع. راجع قيود الخطتين قبل الاعتماد على الموقع لمستخدمين دائمين.

تستخدم نسخة Render متغير `DATABASE_URL` للاتصال بـ Supabase PostgreSQL. اختر Shared Pooler بنمط Transaction على المنفذ `6543` لخدمة الويب الحالية؛ التطبيق يعطل prepared statements. يتم إنشاء الجداول تلقائياً. لا ترفع `app.db` أو `.api_encryption.key` أو `.flask_secret_key` أو `.env` إلى GitHub.

اسم المستخدم الافتراضي للمشرف: `admin`. كلمة المرور تحددها أنت في متغير Render `ADMIN_PASSWORD` ولا تُحفظ داخل المستودع.

## ترحيل قاعدة SQLite القديمة

توجد أداة `migrate_sqlite_to_supabase.py` لنقل الحسابات والمحادثات مع معرّفاتها، وتعليمات النماذج ومفاتيح API المشفرة ومسارات API وملفات Workspace ونقاط استعادة المشاريع وذاكرة Project Intelligence من `app.db` إلى Supabase. راجع قسم الترحيل في دليل النشر، واستخدم قيمة `.api_encryption.key` الأصلية كمتغير `API_ENCRYPTION_KEY` حتى تبقى المفاتيح القديمة قابلة لفك التشفير.

## الفحص الصحي

المسار `/healthz` يفحص اتصال التطبيق بقاعدة البيانات. يجب أن يعيد HTTP 200 مع `{"status":"ok"}`.


## إعداد Alpha 3.1 Max بعد التحديث

إعداد مفاتيح الاتصال للإصدارين يتم من لوحة المشرف. يدعم Alpha 3.1 Max مساراً أساسياً واحتياطياً تلقائياً لكل مفتاح، حتى 8 مفاتيح. تبقى بيانات اعتماد كل مزود منفصلة ولا يجوز إعادة استخدام مفتاح خدمة في خدمة مختلفة. معرّفات النماذج وعناوين الاتصال تُدار من إعدادات التطبيق الداخلية.

تحديث إضافي — Checkpoints وملفات الكود:
راجع الملف ALPHA-CHECKPOINT-CODE-FILES-UPDATE-AR.txt لشرح نقاط الاستعادة التلقائية واليدوية، حدود تخزينها، استرجاع ملفاتها، وتنزيل كتل الكود من المحادثة كملفات منفصلة أو كحزمة ZIP.

تحديث إضافي — أدوات AI Chat، المرحلة الأولى:
راجع الملف PHASE-1-CHAT-TOOLS-REPORT-AR.txt لشرح الأسئلة التفاعلية وWorkspace وحدود التخزين والاختبارات المنفذة. تُنشأ جداول `chat_workspace_files` و`project_checkpoints` و`alpha_project_memory` تلقائياً عند تشغيل التطبيق، وتدعم أداة الترحيل نقل بيانات هذه الجداول من SQLite عند وجودها في قاعدة المصدر، مع الحفاظ على معرّفات المحادثات.

## أدوات Project Intelligence — المرحلة الثانية

أضيفت مجموعة أدوات اختيارية/افتراضية داخل Project Intelligence: Project Files، Code Generation، Code Modification، Code Testing، Error Detection، Debugging، وREADME Generator وRequirements Management وDocker Configuration. يتلقى الكاتب توجيهات الأدوات المحددة ويتحقق المراجع منها، مع بقاء System Prompt العام أعلى أولوية.

Apply Patch يعرض معاينة للتغييرات على ملفات ZIP المرفقة، ثم ينشئ ZIP جديداً بعد تأكيد المستخدم. لا يغيّر الأرشيف الأصلي ولا يرفع التعديلات إلى GitHub. الفحص الحالي ساكن لصياغة Python وJSON وHTML فقط؛ لا ينفذ كوداً ولا يثبت حزمًا ولا يشغل Docker.

راجع `PHASE-2-PROJECT-INTELLIGENCE-TOOLS-REPORT-AR.txt` لتفاصيل الأدوات والحدود والاختبارات.


## بيئة التنفيذ المعزولة — المرحلة الثالثة

أضيفت واجهة Shell / Terminal لتنفيذ الأوامر، وتشغيل ملفات Python، وإنشاء Virtual Environment، وتثبيت الحزم من ملفات Wheel محلية فقط، مع Execution Logs وتنزيل ZIP لمساحة العمل. راجع `PHASE-3-RUNTIME-REPORT-AR.txt` و`DEPLOY-RENDER-SUPABASE-AR.md` و`LIVE-INTEGRATION-CHECKLIST-AR.md` لمعرفة إعداد Render Sandboxes وفحص Supabase وخطوات التفعيل.

ملاحظة: `.env.example` مخصص لملف تشغيل محلي على Termux ويترك `ALPHA_RUNTIME_BACKEND=local`؛ إعداد النشر على Render مصدره `render.yaml` ويستخدم `ALPHA_RUNTIME_BACKEND=render` مع التفعيل.

على Render يستخدم التشغيل مزود Render Sandboxes الرسمي المنفصل عن Flask، مع سياسة شبكة `deny-all` وعدم تمرير أسرار التطبيق. التفعيل الافتراضي للنشر هو `ALPHA_SANDBOX_ENABLED=1`؛ ويلزم إضافة `RENDER_API_KEY` و`RENDER_WORKSPACE_ID` في Environment. لا ينشئ تفعيل العلم Sandbox وحده؛ تُنشأ Sandbox مستقلة عند بدء جلسة تنفيذ من المستخدم. تُنقل ملفات المشروع المختارة إلى Oregon بعد موافقة المستخدم الظاهرة؛ لا ترفق أسراراً أو ملفات حساسة. تثبيت الحزم Offline فقط من ملفات `.whl` تحت `wheels/` أو `wheelhouse/`. لا تعتمد خدمة Render Web على امتيازات `unshare/mount/chroot` داخل حاويتها.

تقرير المرحلة الثالثة — بيئة التنفيذ المعزولة في Alpha
======================================================

الهدف
-----
إضافة بيئة تنفيذ فعلية لأدوات Project Intelligence: Shell وTerminal وCommand Execution وتشغيل ملفات Python وإنشاء Virtual Environment وتثبيت الحزم وعرض Execution Logs، دون تشغيل كود المستخدم داخل صلاحيات عملية Flask أو الوصول إلى أسرار الخادم.

ما أُضيف
--------
1. الملف runtime_sandbox.py: مدير جلسات التنفيذ ومشرف مستقل لكل مساحة مشروع.
2. نقاط API للمستخدم المسجل: GET /api/project-runtime/status وPOST /api/project-runtime/start وPOST /api/project-runtime/execute وGET /api/project-runtime/export/<session_id> وPOST /api/project-runtime/stop.
3. لوحة داخل Project Intelligence باسم Shell · Terminal · Python Runtime، تشمل اختيار الأداة، وبدء مساحة العمل، وتنفيذ الأوامر، وتشغيل Python، وإنشاء البيئة الافتراضية، وتثبيت الحزم، وعرض السجلات، وتنزيل ZIP، وإغلاق الجلسة.
4. اختبارات تكامل في tests/test_runtime_sandbox.py تشمل التشغيل داخل العزل، ومنع الشبكة، وعزل متغيرات أسرار الخادم، وإنهاء عمليات الخلفية العادية، والبيئة الافتراضية، والحزم المحلية، وملكية الجلسات، وتصدير ملفات المشروع.
5. تحديث render.yaml ليكون ALPHA_SANDBOX_ENABLED=0 افتراضياً، وتحديث README-ar.txt ودليل النشر.

طريقة العزل
------------
- يبدأ كل مشروع في عملية Supervisor مستقلة عبر Linux user namespace غير مميز، ثم mount وPID وnetwork وIPC وUTS namespaces.
- يجري إعداد mount propagation خاصة، وchroot لمجلد جذر منفصل، وتُركّب ملفات النظام اللازمة للقراءة فقط.
- ملفات المشروع و/tmp داخل tmpfs منفصلين؛ لا تُركّب شجرة تطبيق Alpha أو قاعدة بياناته أو مفاتيح API أو أسرار البيئة داخل مساحة المستخدم.
- تُزال قدرات Linux من عملية كل أمر، وتُفعّل PR_SET_NO_NEW_PRIVS، ويُضبط PR_SET_DUMPABLE=0 لمشرف الجلسة لمنع عمليات المشروع من قراءة ذاكرته، وتُطبق حدود CPU والذاكرة والملفات والعمليات والواصفات.
- الشبكة معزولة ولا يوجد اتصال خارجي من بيئة المشروع.
- لا يُفعّل زر التشغيل إلا عندما يكون ALPHA_SANDBOX_ENABLED=1 ويجتاز الخادم اختباراً فعلياً لإنشاء user namespace وmount tmpfs وchroot. نتيجة الاختبار تُخزّن مؤقتاً 45 ثانية.
- عند فشل أي شرط لا يوجد fallback إلى تنفيذ الأمر على خادم Flask؛ التشغيل يبقى مغلقاً.

الأدوات وسلوكها
---------------
- Shell / Terminal / Command Execution: ينفذ الأمر كعملية منفصلة داخل المساحة، مع بقاء ملفات المشروع بين الأوامر.
- Python Execution: يشغّل ملف .py من مسار نسبي آمن داخل المشروع، ويستخدم Python الخاص بالبيئة الافتراضية عند وجودها.
- Virtual Environment: ينشئ .venv مؤقتاً باستخدام Python venv دون تنزيل pip.
- Package Installation: يسمح بالتثبيت Offline فقط من ملفات Wheel محلية ضمن wheels/ أو wheelhouse/؛ لا يسمح بعناوين URL أو PyPI أو الشبكة. يلزم إنشاء .venv أولاً.
- Execution Logs: يحتفظ بآخر 40 عملية في الجلسة، ويعرض آخر 20 في الواجهة مع كود الخروج والمدة والمخرجات.
- Download Workspace ZIP: يصدر ملفات المشروع بعد التعديلات، مع استبعاد .venv ومجلدات البناء وملفات الأسرار.

الحدود الحالية
--------------
- حتى 8 مرفقات و20 ميغابايت إجمالاً؛ حتى 500 ملف في ZIP و24 ميغابايت بعد فك الضغط؛ 8 ميغابايت للملف الواحد.
- تُرفض المسارات المطلقة ومسارات اجتياز المجلدات والروابط الرمزية والملفات السرية ومجلدات الاعتماديات/البناء المحددة.
- مساحة المشروع tmpfs حتى 128 ميغابايت و/tmp حتى 32 ميغابايت.
- مهلة الأمر القصوى 20 ثانية، مع حدود CPU و256 ميغابايت مساحة عناوين افتراضية لكل عملية و24 ميغابايت للملف و6 عمليات و64 واصفاً.
- الجلسة تنتهي بعد 20 دقيقة من عدم الاستخدام أو ساعة من إنشائها.
- حتى جلستين متزامنتين إجمالاً، وجلسة واحدة لكل مستخدم، وبحد أقصى 80 عملية تنفيذ لكل جلسة.
- عامل تنظيف خلفي يفحص انتهاء الجلسات كل 30 ثانية، كما تُغلق الجلسات عند خروج عامل التطبيق بشكل سليم عبر atexit.
- الجلسات وسجلاتها مؤقتة ومحفوظة في ذاكرة عملية Gunicorn الحالية. إعادة تشغيل الخدمة تنهي الجلسات؛ أرفق المشروع مجدداً بعد إعادة التشغيل.
- يجب إبقاء عامل Gunicorn واحداً ونسخة خدمة واحدة لهذه البنية الحالية؛ تعدد العمال/النسخ يتطلب نقل مدير الجلسات إلى خدمة تنفيذ مستقلة مشتركة.
- واجهة Terminal الحالية هي Command Runner يحتفظ بملفات العمل بين الأوامر؛ ليست جلسة TTY تفاعلية ببث حي أوامر/مخرجات.
- ملفات .venv لا تُضمّن في ZIP المنزّل. أرفق ملفات Wheel المطلوبة مرة أخرى في بداية الجلسة ضمن wheels/ أو wheelhouse/.

التحقق المنفذ في بيئة العمل الحالية
-----------------------------------
- 92 اختباراً ناجحاً في `python -m unittest discover -s tests -v`، كما نجح التشغيل الشامل عبر `pytest -q` بنتيجة 113 اختباراً و25 حالة فرعية ناجحة؛ لا توجد اختبارات فاشلة.
- شملت الاختبارات جميع اختبارات المرحلة الأولى والثانية والمرحلة الثالثة، واختبارات واجهة الدخول والضوابط الافتراضية والواجهة، واختبارات الترحيل التي تتحقق من نقل `project_checkpoints` و`alpha_project_memory` والحفاظ على `conversation_id`، واختبارات Sandbox التكاملية.
- اختبارات Sandbox أثبتت تشغيل Python وShell داخل chroot، وإنشاء venv، وتثبيت Wheel محلي واستيراده، ومنع الاتصال الخارجي، ومنع توريث متغير سرّي تجريبي من بيئة الخادم، وملكية الجلسة، وفحص ZIP والتصدير.
- فحص Python عبر `py_compile` نجح لجميع ملفات Python في الحزمة، بما فيها ملفات التطبيق والاختبارات.
- فحص JavaScript المضمّن في واجهة التطبيق عبر `node --check` نجح للكتل الثلاث بعد استبدال تعبيرات قوالب Jinja بقيم اختبارية.
- اختبارات تصيير قالب Jinja والتحقق من عدم تكرار معرّفات HTML في صفحات الدخول والمحادثة نجحت؛ جميع معرّفات لوحة Runtime المطلوبة موجودة مرة واحدة.
- لم تتغير requirements.txt ولم تُضف مكتبات خارجية.
- أزيل خيار «مراجعة الأمان» من أدوات استوديو المحادثة بناءً على طلب المستخدم، وأصبحت الأوضاع الخمسة المتبقية متوقفة افتراضياً. لم تُزل ضوابط الحماية الداخلية للتطبيق أو العزل.
- نُقلت إعدادات الكاتب والمراجع ودورات المراجعة والتفكير وأدوات Project Intelligence إلى أسفل نموذج المهمة. لا يحسب التطبيق تكلفة مالية حتى الآن؛ يعرض عدد الاستدعاءات والاستخدام المعلن من الخدمة فقط، ولا يخترع تسعيراً نقدياً.
- أصبح خط المراحل المكتملة أخضر كما طُلب.
- لم تُحذف ملفات الحزمة الأصلية؛ بقي PHASE-3-REPORT-AR.txt الخاص بخريطة المشروع دون تغيير، لأن هذه ميزة مختلفة عن بيئة التنفيذ الحالية.

ما لم يتم التحقق منه
--------------------
- لم يكن Flask وGunicorn مثبّتين في بيئة الفحص الحالية؛ لذلك لم يتم تشغيل تطبيق WSGI أو اختبار نقاط API عبر HTTP أو تصفح الواجهة داخل متصفح حقيقي.
- لم يتم النشر إلى Render ولم يتم اختبار صلاحيات user namespaces داخل حاوية Render أو خطة Render المستخدمة.
- لم يتم تشغيل Flask/WSGI أو اختبار HTTP حي في بيئة الفحص لأن Flask وGunicorn غير مثبّتين هنا. وجود الأدوات في صورة النظام لا يثبت أن المضيف يسمح بإنشاء namespaces أو mounts.
- لا تفعّل ALPHA_SANDBOX_ENABLED=1 على Render إلا بعد النشر وفحص /api/project-runtime/status والتأكد من نجاح اختبار العزل؛ إذا فشل، ستظل الميزة معطلة ولا تستخدم تنفيذاً احتياطياً غير معزول.
- لم يتم اختبار مشاريع كبيرة أو أحمال متعددة المستخدمين أو عمليات بناء تتجاوز الحدود المذكورة.

**ملاحظة أمنية:** Linux namespaces وchroot توفر عزلاً متعدد الطبقات، لكنها ليست آلة افتراضية مستقلة؛ ما زالت تشترك مع المضيف في نواة Linux. لذلك اعتبر هذه المرحلة بيئة تشغيل محدودة للتجربة والمشاريع الموثوقة نسبياً، وليست حداً أمنياً نهائياً لاستضافة شيفرات عدائية من جمهور مفتوح. عند فتح التشغيل لمستخدمين عامّين أو أحمال عالية المخاطر، انقل المشغّل إلى خدمة منفصلة تستخدم microVM/VM مؤقتة أو بنية Sandbox مخصصة مع سياسات موارد ومراقبة مستقلة.


تحديث نشر Render: أصبح مزود الإنتاج Render Sandboxes الرسمي باستخدام SDK `render>=1.8.0`، بدلاً من محاولة تنفيذ user namespaces/chroot داخل عملية Web Service. تظل Sandbox معطلة افتراضياً وتستخدم `network_policy=deny-all`. يلزم اختبار الحي عبر `render_sandbox_probe.py` قبل التفعيل. راجع LIVE-INTEGRATION-CHECKLIST-AR.md.
